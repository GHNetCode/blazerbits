Self-Healing Lab

A team of four small agents working together with an LLM to help test & resolve scripts in a disposable MicroVM.

The LLM never decides if the test passes or fails. The results (pass or fail) only come from the sandbox that the agents read from.

4agents
20bugged practice apps

How it works

The agents accept submitted tasks communicating with each other via a shared SQLite DB where they then access the sandbox through the Control-Plane (NodeJS Environment) to perform testing, attempting to fix the script.

Agents

The Agents, SQLite and Ollama all run as an ordinary user and never execute the code directly during testing. The code only runs inside the sandbox, separated by the Control Plane.

⇄HTTP

fc-core (Control Plane)

The Node.js server on port 3000. It is the only part with admin/root rights: it mounts the image, boots the VM and cleans up.

⇄SSH

Firecracker MicroVM (Sandbox)

Has its own kernel and no internet. Built from a small Alpine image and deleted after every run.

Agents know one call: POST /sandbox/run. The sandbox technology can change without touching an agent.

Journey resolving a bug

Step 1

Submit a task

cli.submit or cli.submit_prompt writes a task to the inbox file for the script to be checked. The Supervisor then moves it into the tasks table.

Step 2

Test Engineer

Picks up the task and runs the script in a fresh sandbox. Exit code 0 means the script ran successfully. Anything else opens an incident.

Step 3

Debugger

The incident is passed to the Debugger, which reads the source, runs a static check and asks the LLM what is wrong. It then proposes a fix but edits nothing.

Step 4

Repair

The Repair agent copies and patches the submitted script, then runs the real test in a new sandbox. If it fails, the task goes back to the Debugger for further diagnosis.

Step 5

Confirm

The Test Engineer tests the patched script. A pass resolves the incident. After five failed rounds it is escalated to a person.

What submit_prompt asks

  • B: Path & params used to run the script
  • B2: How many times to submit this task
  • C1: Exit code
  • C2: Text expected in the console output
  • C3: Files the script should create
  • C4: Key words inside those files
  • C5: Treat a miss in C2 to C4 as a "Caution" instead of a real failure

Recovery

  • Each agent reports a heartbeat every 3 s
  • No heartbeat for 47 s puts its task back in the queue
  • Tasks past 480 s are re-queued
  • The Supervisor relaunches dead agents without using the model

Staying stable

  • One heavy job at a time, with pauses between jobs
  • Model calls and sandbox boots take turns sharing one file lock
  • A resource check on disk, memory and CPU before each boot
  • VM capped at 95% CPU. The latest 15-cycle test ran without a freeze

Working

Repair loop

When a test fails, the lab diagnoses the problem, fixes a copy of the script and tests it in a new sandbox. A failed fix goes back for another attempt, up to 5 rounds. Your real files are only updated once a fix passes, and the Test Engineer then re-runs the script to confirm.

Working

Supervisor

Watches every agent’s heartbeat. If an agent crashes or hangs, its task goes back in the queue to be picked up again, the agent is restarted, and a task that keeps failing is escalated to a person.

Built, off by default

Audit trail

An optional, off-by-default record of everything the lab did: every task, model prompt and reply, sandbox run and applied fix. Entries are chained with hashes, so any later edit can be detected. Replay a whole incident with cli.audit_report.

Available

Bug Zoo

Twenty deliberately bugged apps with an answer key. Comes with an install script that makes it easy to revert fixed scripts to their bugged state for further testing.

Roadmap

Three steps, in this order. Each builds on the one before.

Next

RAG (Retrieval-Augmented Generation)

Today the Debugger reads the source directly and remembers nothing. RAG will first look up the most relevant code and past incidents (the failure, the diagnosis and the fix that worked) and give them to the model along with the new failure.

The lab will keep a searchable index of this material, like the index of a book. It lives outside agents.db, so searching never slows the agents down. Work starts in /source_files.py and the Debugger’s prompt builder.

Then

MCP server (Model Context Protocol)

MCP is a standard way for an AI assistant to use outside designated tools that the lab will offer.: submit a spec check, list incidents and their status, read an audit report, and read a file in a test project.

It goes through the same entry points as the command line, so an assistant has no shortcut into the database. Any change it makes is subject to the same checks as today.

After

Agentic layer

A "Team Lead" that takes a goal such as "make these five scripts pass", writes the specs, submits them, watches incidents and reports back.

It sits on top of the MCP tools. The Supervisor stays as it is, so the lab keeps working if the model stalls.
